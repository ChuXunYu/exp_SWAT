# 计划审查报告（v12 r4）

## 审查结果
REJECTED

## 发现
- **[严重]** — 任务没有把学习计划创建/修改详情的日期输入形态收束到唯一可执行的服务接口。当前文本要求“创建、修改和更新进度的非法输入应转换为 `OperationResult.failure(ErrorCode.VALIDATION_ERROR, ...)`”，任务上下文又明确需要处理“截止日期早于开始日期”等创建边界；但 `StudyPlan` 既有实体和已完成设计只接受 `DateRange`，本轮任务也没有明确 `StudyPlanService` 的创建/修改详情方法应接收原始 `startDate`、`endDate`（或等价原始输入对象）。如果 coder 延续现有模块风格直接让服务公开接口接收 `DateRange`，那么“开始日期晚于截止日期”的异常会在调用方构造 `DateRange` 时先抛出，根本无法在服务边界转换成 `OperationResult`，相应测试也无从编写。当前任务因此仍存在两条实现路径，且其中一条无法满足本轮行为契约。
- **[严重]** — 任务只把“创建学习计划”的初始进度接口固定为原始整数，却没有对“更新进度”公开接口做同样收束，导致非法进度映射规则仍然不完整。文本一方面要求“创建、修改和更新进度的非法输入应转换为 `VALIDATION_ERROR`”，另一方面只规定创建接口接收原始整数初始进度；对于 `StudyPlanService.updateProgress(...)`，coder 仍可以沿用领域实体的 `Progress` 参数。如果这样实现，`-1`、`101` 这类原始非法进度值同样会在服务调用前就无法表示，服务层无法承担统一错误映射职责，也无法对白盒边界形成稳定测试契约。

## 修改要求（仅 REJECTED 时）
1. 明确 `StudyPlanService` 的创建和修改详情公开接口必须接收原始开始日期与截止日期（或唯一等价的原始请求对象），并要求服务内部负责构造 `DateRange`，从而把“开始日期晚于截止日期”稳定映射为 `OperationResult.failure(ErrorCode.VALIDATION_ERROR, ...)`；同时补充该失败路径及失败后仓储状态不变的测试要求。
2. 明确 `StudyPlanService.updateProgress(...)` 的公开接口与创建接口保持一致，固定接收原始整数进度值，由服务内部转换为 `Progress.of(...)`；补充更新进度对 `0`、`100`、`-1`、`101` 的成功/失败行为以及失败后仓储状态不变测试，消除“服务接收 `Progress` 还是接收原始整数”的实现分叉。
