# QA 风险修复需求澄清 v1

本需求基于 `/root/exp_SWAT/diags/202606131007_qa-risk-diagnosis/diag_v1.md`、诊断质询结果、原始需求文档、OOD 设计、README 和完整验收报告整理而成。目标不是重新设计整个 Java AI 个人学习与生活助手，也不是把所有风险都转化为本轮开发任务，而是把已经确认存在、对当前交付质量有实际影响、且适合在一轮内实现和验证的问题，澄清为清晰、可实现、可测试的修复需求。

当前项目整体构建和测试状态较好，验收记录显示 Maven 测试、验证和 CLI smoke 均已通过；因此本轮修复应优先补齐用户主流程和明显一致性缺口，避免对稳定业务做大规模重构。基于诊断结论，本轮必须修复的范围包括：AI 结构化草稿端到端生成入口、学习计划草稿 breakdown 导入不落地、任务草稿 dueDate 规则不一致、摘要页紧急事项覆盖不足、中文控制台输入和输出体验不一致。ConsoleApplication 大规模拆分、持久化事务边界和低耦合功能裁剪不作为本轮开发任务。

## 本轮必须修复的问题

### 1. 补齐 AI 结构化草稿端到端生成入口

用户问题是：需求要求 AI 生成的任务建议或学习计划拆解应先成为草稿，再由用户确认导入；但当前用户在控制台中只能进入通用 AI 问答或管理已有草稿，无法从“向 AI 提出结构化生成请求”自然走到“生成草稿、查看草稿、确认导入”的完整流程。

当前行为是：`AI 问答`入口只返回自然语言回复，不解析结构化建议，也不保存草稿；`AI 草稿`菜单只支持列表、查看、确认、取消等管理已有草稿的操作。项目中已有结构化解析器、草稿实体、草稿仓储、生命周期服务和导入服务，但缺少串联 AI 调用、解析、草稿编号、草稿保存和 CLI 可见性的应用入口。

目标行为是：用户应能在控制台中选择生成结构化任务草稿或学习计划草稿，输入自然语言目标或需求后，系统调用 AI 的结构化场景，解析返回结果，生成 `SuggestionDraft` 并保存到草稿仓储。生成成功后，草稿应能立即在草稿列表中看到，并可沿用既有查看、确认导入、取消和重复确认保护流程。若 AI 未配置、调用失败、返回空响应、返回非结构化内容或结构化内容不合法，系统应给出明确失败结果，不应创建不可用草稿，也不应修改正式任务或学习计划数据。

基于现有设计推断，本功能需要新增或补齐一个应用层服务来编排 AI 调用、提示词/场景、`StructuredSuggestionParser`、`SuggestionDraftRepository` 和 `IdGenerator`；CLI 只应作为入口和展示层，不应把解析和保存规则直接写在菜单逻辑里。

验收标准：

- 用户可从控制台进入“生成任务草稿”和“生成学习计划草稿”一类的结构化生成入口。
- AI 返回合法任务草稿时，系统保存一个可查看、可确认导入的任务草稿；确认后正式任务数据增加，取消后正式任务数据不变。
- AI 返回合法学习计划草稿时，系统保存一个可查看、可确认导入的学习计划草稿；确认后正式学习计划数据增加，取消后正式学习计划数据不变。
- AI 未配置、超时、鉴权失败、限流、空响应、格式异常或结构化校验失败时，用户能看到稳定错误提示或错误分类，草稿仓储和正式业务数据不被污染。
- 重复确认、取消后确认、导入失败回滚等既有草稿生命周期规则仍保持有效。

影响模块包括 `assistant.ai`、`assistant.app` 和应用装配相关类。若实现需要扩展提示词场景或 AI 场景枚举，也应限制在 AI 模块和应用装配边界内。

必须补充或更新的测试包括：

- 服务层端到端单元测试：fake AI 返回任务草稿 JSON 后解析、分配草稿 id、保存草稿。
- 服务层端到端单元测试：fake AI 返回学习计划草稿 JSON 后解析、分配草稿 id、保存草稿。
- 失败路径测试：AI 未配置、空响应、格式异常、结构化字段非法时不保存草稿。
- CLI 测试：用户从结构化生成入口创建草稿后，草稿菜单能列出并查看该草稿。
- 回归测试：生成后的草稿确认导入、取消、重复确认仍符合既有生命周期规则。

### 2. 明确并落地学习计划草稿 breakdown

用户问题是：AI 生成学习计划时给出的拆解步骤已经能被解析和展示，但用户确认导入后，这些步骤没有进入正式数据，导致 AI 输出中最有价值的计划拆解被浪费。

当前行为是：`StudyPlanDraftContent` 保存 `breakdown`，解析器会读取 JSON 中的 `breakdown` 数组，草稿详情页也能展示 breakdown；但 `DraftImportService.importStudyPlan()` 导入正式学习计划时只使用目标、开始日期、截止日期、预期小时和初始进度，没有使用 breakdown。正式学习计划模型当前也没有直接保存 breakdown 的字段。

目标行为是：本轮需要为 breakdown 定义一个明确、可测试的落地方向，并在导入时执行。考虑到当前正式学习计划模型没有 breakdown 字段，而任务模块天然承载可执行步骤，建议本轮将学习计划草稿中的 breakdown 转换为与该学习计划目标相关的待办任务，或采用项目内已有的等价正式数据结构保存。若实现者选择不生成任务而是扩展学习计划模型保存步骤，也必须保证步骤在导入后可查看、可测试，并且不会只停留在草稿层。

本需求不强制规定每个 breakdown 项的字段级生成策略，但导入规则必须一致：非空 breakdown 项不得在确认导入时静默丢弃；空 breakdown 或缺失 breakdown 可以只创建学习计划，不应导致导入失败。若将 breakdown 转为任务，任务标题、描述、优先级和 dueDate 的生成规则必须稳定，不能依赖展示层临时拼接；其中 dueDate 应遵守本需求第 3 项的统一规则。

验收标准：

- 带有 breakdown 的学习计划草稿确认导入后，用户能在正式数据中看到这些拆解步骤的落地结果。
- breakdown 中的空字符串或空白项应被忽略或在解析阶段清洗，不应生成空任务或空步骤。
- 无 breakdown 的学习计划草稿仍可正常导入为正式学习计划。
- 如果 breakdown 落地过程中任一正式数据创建失败，导入结果必须可解释，不能出现学习计划已创建但步骤部分丢失且用户无感知的状态。基于当前内存实现，可使用补偿或先校验后写入保证一致性。

影响模块包括 `assistant.ai` 的草稿内容和导入服务、`assistant.study`，以及在选择转任务方案时涉及的 `assistant.task`。

必须补充或更新的测试包括：

- `DraftImportService` 测试：带 breakdown 的学习计划草稿导入后，breakdown 被保存或转化为正式可见数据。
- `DraftImportService` 测试：无 breakdown 或空 breakdown 的学习计划草稿仍能导入。
- 失败路径测试：breakdown 落地失败时不产生静默丢失。
- CLI 或服务查询测试：用户导入后能通过正式模块查看 breakdown 的落地结果。

### 3. 统一任务草稿 dueDate 规则，避免可查看但不可导入的草稿

用户问题是：AI 任务草稿详情允许显示“截止日期：未设置”，但正式任务模型和导入服务要求 dueDate 非空。用户看到草稿后尝试确认导入会失败，且当前草稿菜单没有编辑或补全入口，体验上像是系统生成了一个无法使用的草稿。

当前行为是：任务草稿模型和结构化解析器允许 `dueDate == null`；控制台草稿详情对空 dueDate 显示“未设置”；导入服务在确认任务草稿前要求每个任务项 dueDate 非空，否则整个导入失败。当前测试也分别固定了“可解析为空”“展示未设置”和“导入失败”这三个行为。

目标行为是：任务草稿的 dueDate 规则应在生成和确认链路中保持一致。本轮建议采用更稳妥的规则：可进入“可确认状态”的任务草稿必须具备合法 dueDate；AI 结构化生成或解析时如果任务项缺少 dueDate，应在保存草稿前拒绝该草稿，或按明确规则补全 dueDate 后再保存。考虑到正式任务需求明确包含截止日期，且草稿菜单暂无编辑补全能力，本轮不应继续保存“用户无法确认导入”的任务草稿。

如果实现选择自动补全 dueDate，规则必须明确、可解释、可测试，例如基于用户输入中的日期、学习计划结束日期、或当前日期加固定偏移推导；不能使用随机日期或依赖 AI 自然语言解释。若无法可靠补全，应拒绝保存草稿并提示 AI 返回缺少必需字段。

验收标准：

- 新生成或新解析并保存的任务草稿中，每个任务项都具有合法 dueDate。
- 缺少 dueDate 的 AI 任务草稿响应不会保存为可确认草稿，或会按明确规则补全后保存。
- 用户在草稿列表中看到的可确认任务草稿，确认导入时不应再因为 dueDate 缺失失败。
- 既有正式任务模型仍保持 dueDate 必填，不引入无截止日期正式任务。
- 草稿详情页不再把新生成的可确认任务草稿展示为“截止日期：未设置”；若保留对历史或测试数据的展示兼容，也必须明确这类草稿不可确认或会给出清晰原因。

影响模块包括 `assistant.ai` 的任务草稿模型、结构化解析、结构化生成服务、导入服务，以及 `assistant.app` 的草稿展示和错误提示。

必须补充或更新的测试包括：

- 解析或生成服务测试：缺少 dueDate 的任务草稿响应被拒绝保存，或被明确规则补全。
- 导入服务回归测试：可保存的任务草稿确认导入不会因 dueDate 缺失失败。
- 控制台测试：缺 dueDate 场景向用户显示清晰错误，而不是生成一个看似可用的草稿。
- 保留正式任务 dueDate 非空约束的回归测试。

### 4. 摘要页增加逾期未完成任务和未来高优先级任务

用户问题是：摘要页本应帮助用户快速看到真正紧急的事项，但当前只展示今日到期任务，逾期未完成任务和未来几天的高优先级任务不会突出显示。用户可能因此错过比今日普通任务更重要的事项。

当前行为是：`SummaryService.getDashboardSummary()` 对任务只查询 `TaskQuery.byDueDate(today)`；`DashboardSummary` 没有逾期任务和未来高优先级任务字段；CLI 汇总页也只展示今日任务数等摘要信息。AI 本地上下文也间接受此影响，因为它依赖同一个汇总结果。

目标行为是：摘要应在保留今日任务的基础上，增加两个紧急视图：逾期未完成任务、未来 7 天内到期的高优先级未完成任务。这里“未来 7 天”基于当前日期计算，不包含已经逾期的任务；是否包含今天可由实现统一定义，但文档和测试必须一致。基于常见用户理解，建议逾期任务指 dueDate 早于今天且状态未完成；未来高优先级任务指 dueDate 在今天至今天后 7 天范围内、优先级为 HIGH、状态未完成的任务。

摘要页应避免重复计数造成混乱：同一任务如果同时满足今日任务和未来高优先级任务，可以在不同栏目展示，但计数和标题应让用户理解其含义。AI 本地上下文也应包含这些紧急任务摘要，使 AI 建议能感知逾期和即将到期的高优先级任务。

验收标准：

- 摘要数据结构能表达今日任务、逾期未完成任务、未来 7 天高优先级未完成任务。
- CLI 汇总页能显示逾期未完成任务数量和未来 7 天高优先级任务数量；如项目已有列表展示习惯，也应显示任务标题或关键摘要。
- 已完成的逾期任务不应出现在逾期未完成任务中。
- 低/中优先级的未来任务不应出现在未来高优先级任务中。
- AI 本地上下文包含逾期和未来高优先级任务信息。

影响模块包括 `assistant.summary`、`assistant.task` 查询能力或查询组合、`assistant.app` 的汇总展示，以及 AI 本地上下文构造相关测试。

必须补充或更新的测试包括：

- `SummaryService` 测试：逾期未完成任务被纳入摘要。
- `SummaryService` 测试：已完成逾期任务被排除。
- `SummaryService` 测试：未来 7 天 HIGH 且未完成任务被纳入摘要，非 HIGH 或超出窗口任务被排除。
- CLI 汇总展示测试：输出包含逾期和未来高优先级任务栏目。
- AI 本地上下文测试：上下文文本或结构中包含新增紧急任务信息。

### 5. 改善中文控制台输入和输出中的英文枚举暴露

用户问题是：应用面向中文命令行用户，但多个输入提示、错误提示和输出详情直接暴露 `LOW/MEDIUM/HIGH`、`TODO/COMPLETED`、`INCOME/EXPENSE` 等英文枚举。用户需要理解内部枚举名才能操作，中文交互体验不一致。

当前行为是：任务优先级、任务状态、日程状态、学习计划状态、收支类型等路径中，部分新增、修改、筛选和详情展示直接要求或展示英文枚举。新增收入/支出已经通过菜单分开，不是主要问题；主要问题集中在修改、筛选、错误提示和列表/详情输出。

目标行为是：控制台应支持中文别名输入，并优先以中文展示枚举含义。为兼容已有测试、文档或熟悉英文枚举的用户，可以继续接受英文枚举作为别名，但中文应成为默认提示和输出形式。例如优先级可支持“低/中/高”和 `LOW/MEDIUM/HIGH`，任务状态可支持“未完成/已完成”和 `TODO/COMPLETED`，收支类型可支持“收入/支出”和 `INCOME/EXPENSE`。具体用词可以按现有中文菜单风格调整，但同一枚举在输入提示、错误提示、列表和详情中应保持一致。

本需求不要求做复杂国际化框架，也不要求引入资源文件。基于当前项目规模，可以通过集中解析和格式化方法实现，避免在各菜单分支散落硬编码映射。

验收标准：

- 用户可以用中文输入任务优先级、任务状态、日程状态、学习计划状态和收支类型等常见枚举条件。
- 控制台列表、详情和错误提示优先显示中文含义，而不是内部英文枚举名。
- 既有英文枚举输入如果保留，应作为兼容别名继续可用。
- 非法输入时，错误提示应列出中文可选值，并可附带英文别名。
- 改动不影响业务服务层枚举建模，服务层仍可使用类型安全枚举。

影响模块主要是 `assistant.app` 的输入解析、输出格式化和相关控制台测试；如已有通用解析工具，可同步调整。

必须补充或更新的测试包括：

- 控制台测试：中文优先级、状态、收支类型等输入可被正确解析。
- 控制台测试：列表和详情输出显示中文枚举含义。
- 控制台测试：非法枚举输入显示中文错误提示。
- 回归测试：英文枚举别名仍可用，或如决定移除英文输入，应同步更新文档并确保所有测试反映新规则。

## 建议后续修复的问题

ConsoleApplication 大规模拆分属于真实的可维护性风险，但不是当前功能缺陷。该类承担了大量菜单、输入解析、输出格式化和服务调用，后续新增 AI 草稿入口和中文枚举映射时应尽量通过小型私有方法或局部 helper 控制膨胀；但本轮不应为了重构而重构。建议在上述功能修复稳定后，再规划一次控制台层重构，将任务、日程、学习计划、收支、笔记、AI 草稿等菜单拆成独立 handler 或 presenter，并以现有 `ConsoleApplicationTest` 作为回归保护。

草稿导入缺少真正事务边界也建议后续处理。当前内存实现已有 best-effort rollback，并有测试覆盖任务导入失败后的清理，因此不应描述为当前必然产生部分导入。但如果后续引入数据库、文件持久化或跨仓储事务，就需要重新定义导入业务数据和草稿状态更新的原子性，避免导入成功但草稿状态保存失败造成重复导入。本轮只需要在新增 AI 草稿生成和 breakdown 落地时不削弱现有补偿行为。

真实 DeepSeek 连通性测试目前仍是验收风险，但原始本轮要求主要聚焦 QA 风险修复，且默认单元测试不应依赖网络和 API Key。因此建议后续通过 `*IT.java` 和 Maven integration profile 增加可选集成测试，条件启用真实 API Key，验证 base_url、模型配置和最小可用响应；不应作为本轮默认测试通过的前提。

测试文档中的历史测试数量口径不一致属于文档维护问题，建议后续同步 README、测试计划和缺陷回归文档，或改写为“以当前 Surefire 输出为准”。如果本轮修复新增测试导致测试数量变化，也应避免在多个文档中硬编码易过期数字。

## 只需文档说明或暂不处理的问题

收支、笔记搜索等功能相对 AI 学习助手主线耦合较低，但它们已经是当前需求定义的 8 个核心功能的一部分，并且验收报告判定相关功能通过。本轮不应裁剪这些模块，也不应把“低耦合”当成缺陷修复。若后续要产品化收敛范围，应先重新修订产品需求，而不是在 QA 修复轮中删除已交付功能。

数据持久化、导出、账号、多用户、云同步、真实系统通知、图形界面、健康信息和联系人管理都不属于当前版本范围。与这些能力相关的事务、权限、同步和长期数据管理问题，本轮暂不处理。

## 本轮整体验收要求

完成本轮修复后，应至少在 `java-ai-assistant/` 下通过默认 `mvn clean test`。如果改动影响 Maven verify、JaCoCo 或 CLI smoke，也应同步验证。默认测试仍不得依赖真实 DeepSeek 网络、真实 API Key 或不可控当前时间。

本轮新增或修改的测试应覆盖服务层业务规则和必要的 CLI 用户路径，不能只修改展示文本。尤其是 AI 结构化草稿生成入口，应具备 fake AI 驱动的端到端单元测试，证明“AI 响应 -> 解析 -> 保存草稿 -> 用户确认导入”的链路在本地可重复验证。

本需求不要求直接修改代码；它用于指导后续实现 agent 或开发者进行修复。实现时若发现某个目标行为与现有领域模型存在冲突，应优先保持正式业务数据一致性和测试可复现性，并在实现文档或提交说明中说明选择。
