# 验收清单与下一阶段迭代需求澄清

本任务的核心目标不是继续修改 Java 源码，而是在当前已完成实现的基础上，整理一份面向产品级验收和后续迭代规划的文档。输出文档应写入 `/root/exp_SWAT/docs/3 acceptance-and-next-iteration.md`，作为需求文档、架构设计、技术方案、实现计划和当前代码交付状态之后的第三份总结性文档。

用户明确要求文档基于“当前已完成实现”，因此编写时不能只复述最初需求，也不能假定所有计划项都已经完成。应结合仓库中的参考资料和现有工程实际状态来判断当前版本的交付范围。参考资料包括 `/root/exp_SWAT/docs/1 requirement.md`、`/root/exp_SWAT/docs/2 design-oo.md`、`/root/exp_SWAT/designs-tech/202606111332_java-ai-assistant-tech/tech_v2.md` 和 `/root/exp_SWAT/implements/202606110715_java_ai_assistant_full_dev/plan.md`。基于当前仓库可见状态推断，`java-ai-assistant/` 已是一个 Java 17、Maven 单模块命令行应用工程，已经形成较完整的源码、单元测试、测试报告、覆盖率产物和配套文档；验收文档应围绕这一实际交付物展开，而不是重新设计系统。

这份验收与迭代文档的读者是课程项目验收者、开发者和后续迭代执行者。文档需要回答三个问题：当前版本到底交付了什么；从用户视角和质量视角应如何逐项验收；当前版本之外还有哪些明确边界和下一阶段优先事项。文档应可直接指导人工验收、测试复核和后续需求排期，因此所有条目都必须具体、可验证、可执行，避免使用“体验良好”“功能完善”“性能较好”这类无法直接判断的表述。

当前版本交付范围应覆盖 Java AI 个人学习与生活助手的既有实现边界。应说明该版本是单用户、本地运行、命令行交互的 Java 应用，使用 Maven 构建，普通单元测试不依赖真实 DeepSeek、网络、API Key 或真实当前时间。功能范围应至少按照原需求中的 8 个核心能力来说明：AI 问答与学习生活建议、AI 结构化建议确认导入、任务待办管理、日程提醒管理、学习计划管理、收支记录管理、个人笔记或日记管理、数据查询与汇总统计。若当前实现中还包含应用装配、演示数据、控制台入口、环境说明、测试计划、测试用例、缺陷回归文档、JaCoCo 覆盖率报告或 CI/文档交付测试等内容，也应作为交付支撑能力列入，但不要把它们混同为新的用户业务功能。

用户视角核心场景验收清单应按真实使用路径组织，而不是只列类名或测试类名。每个验收项都应包含可执行操作、前置条件或输入、期望结果。典型核心场景包括：启动命令行程序并看到可用菜单；创建、查询、修改、完成、撤销完成和删除任务；创建日程并按日期查询，验证时间冲突和即将开始、进行中、已过期状态；创建学习计划并更新 0%、100% 和中间进度，验证逾期或完成状态；记录收入和支出并按类别、日期范围统计收入总额、支出总额和结余；新增、查询、修改、删除笔记并按关键字或标签检索；查看今日任务和日程、本周学习计划、本月收支、笔记标签分布等汇总信息；在 AI Key 未配置或使用 fake/mock 的情况下验证 AI 问答、笔记摘要或结构化建议流程的可测试行为；对 AI 生成的任务或学习计划草稿执行确认导入、取消导入和重复确认等操作。

异常场景验收清单应覆盖用户输入错误、业务状态冲突、外部依赖失败和数据一致性保护。应明确检查空标题、空内容、非法日期、开始日期晚于结束日期、日程结束时间不晚于开始时间、金额为 0 或负数、金额小数位非法、未知或空收支类型、进度小于 0 或大于 100、关键字为空、记录不存在、删除不存在、重复完成、重复撤销、重复确认草稿、取消后再确认草稿、AI 返回空响应、AI 返回格式异常、AI 未配置、鉴权失败、限流、超时、远端不可用等情况。每个异常验收项都应说明期望错误分类或可观察结果，例如返回 `VALIDATION_ERROR`、`NOT_FOUND`、`STATE_CONFLICT`、`SCHEDULE_CONFLICT`、`AI_NOT_CONFIGURED`、`AI_TIMEOUT` 等稳定错误码，并验证失败操作不会污染已有本地数据。

非功能验收项应面向课程实验和工程质量，而不仅是运行结果。文档应包含构建与测试验收，例如在 `java-ai-assistant/` 工程执行 Maven 测试命令能够通过，单元测试不访问真实网络和 API Key，Surefire 报告存在且测试结果可复核，JaCoCo 覆盖率报告能够生成或已存在，测试用例覆盖核心业务逻辑、边界输入、状态变化、跨模块汇总和 AI 外部依赖失败处理。还应覆盖代码结构验收，例如控制台层不承载核心业务判断，业务服务返回可断言的结果，仓储默认使用内存实现，查询结果以只读视图或不可修改快照暴露，当前时间、编号和 AI 客户端可替换，API Key 不硬编码。对于可维护性和可演示性，应要求 README、环境说明、测试计划、测试用例、缺陷回归说明等文档与实际工程一致。

文档需要明确当前版本不属于验收范围的边界。基于原始需求和技术方案，本版本不要求账号登录、多用户、云端同步、数据库持久化、文件导出、真实系统通知、移动端界面、复杂权限、健康信息管理、联系人或常用信息管理、训练或微调模型、复杂智能体框架。真实 DeepSeek API 连通性如存在，应作为可选集成验证，不能作为普通单元测试通过的前提。若当前实现中尚未完成某些计划中的扩展项，验收文档应把它们放入下一阶段迭代建议，而不是写成当前已交付能力。

下一阶段优先级建议需要按 P0/P1/P2 分层，并给出每项为什么需要做、完成后如何验收。P0 应放置阻塞最终课程提交或产品级验收的事项，例如补齐与实际代码一致的验收文档、确认全部 Maven 单元测试通过、确认覆盖率报告和测试文档可复现、修正任何当前版本核心场景无法运行或文档与实现不一致的问题。P1 应放置能显著提升交付质量但不一定阻塞当前验收的事项，例如增强控制台交互可用性、补充真实 DeepSeek 集成测试 profile、完善异常提示、补充端到端演示脚本、扩展缺陷回归记录。P2 应放置后续增强或可选产品化方向，例如可选持久化、导入导出、更丰富的 AI 场景、图形界面、更多统计图表、长期数据管理等。

由于用户要求“如需提交文档改动，提交并推送 GitHub”，该要求应理解为后续执行阶段的交付约束：在实际生成 `/root/exp_SWAT/docs/3 acceptance-and-next-iteration.md` 后，应检查 Git 状态，提交该文档改动并尝试推送到 GitHub；如果推送失败，应在执行结果或验证记录中说明原因。需求澄清文档本身只定义要产出的内容和验收标准，不直接执行提交推送。

最终文档应使用清晰的 Markdown 组织，建议包含“当前版本交付范围”“用户视角核心场景验收清单”“异常场景验收清单”“非功能验收项”“不属于当前版本的明确边界”“下一阶段优先级建议 P0/P1/P2”等章节。清单条目应尽量使用表格或编号列表，至少包含验收对象、操作或检查方式、预期结果；若某项依赖环境变量、网络或 API Key，应明确标注为可选集成验收或人工验证，不得与默认离线单元测试混淆。
