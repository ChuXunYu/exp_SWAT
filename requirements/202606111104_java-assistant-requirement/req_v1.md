# Java 个人学习与生活助手需求文档

本需求文档面向“软件质量保证与测试”课程实验使用，目标是为实验 1 和实验 2 提供一个适合 Java 实现、功能数量充足、便于开展白盒与黑盒测试的待测应用需求。用户原始需求明确要求“适用 Java”“功能不少于 8 个”“尤其着重测试部分”，因此本文档重点说明应用应完成什么功能、应满足哪些质量要求，以及后续测试计划、测试用例、测试结果分析应围绕哪些内容展开。

## 需求背景与目标

本项目需要开发一个简单但结构清晰的个人助手程序，用作“软件质量保证与测试”课程实验的待测对象。根据实验指导书，实验 1 需要完成应用程序编码、制定测试计划、设计并运行白盒测试用例，实验 2 需要在实验 1 应用的基础上制定黑盒测试计划、设计并手工执行黑盒测试用例。课程评分标准特别关注测试计划、测试用例设计、测试结果分析、待测程序编码规范和实验报告规范，因此待测应用不能只是功能展示，还应具备可拆分、可测试、可分析的业务逻辑。

本应用建议定位为“大学生个人学习与生活助手”。该定位是基于课程实验场景和“个人助手程序”要求作出的合理推断：开发者和演示者通常是学生，选择学习、任务、日程、收支、健康、笔记等功能，既贴近目标用户，也便于构造正常输入、异常输入、边界值、组合流程和状态变化等测试场景。

程序应使用 Java 开发。默认可以实现为命令行交互程序，以降低界面复杂度并突出业务逻辑和测试设计；如小组希望使用 Swing、JavaFX 或 Web 界面，也应保证核心业务逻辑与界面层分离，使 JUnit 单元测试能够直接覆盖核心类和方法。无论采用哪种界面形式，需求重点都是一个可运行、可演示、可测试的 Java 待测程序，而不是单纯的文档或伪代码。

## 目标用户与使用场景

目标用户是需要管理日常学习和生活信息的大学生。用户希望在一个轻量工具中记录待办任务、课程或日程、学习计划、收支、健康情况和个人笔记，并能查询、修改、删除、统计这些信息。程序应支持用户在本地完成基本数据管理，不要求联网、多人协作或复杂权限控制。

典型使用场景包括：用户添加一项课程作业并设置截止日期，随后查看未完成任务；用户记录一笔午餐支出并查看本月收支汇总；用户登记一次运动或睡眠记录并查看健康趋势；用户添加学习计划并标记完成进度；用户通过关键字查询笔记；用户在测试或答辩时按功能模块演示输入校验、异常提示、查询统计和数据变化。

## 功能需求

应用至少应实现 8 个可独立演示和测试的功能模块。为了保证功能数量和测试覆盖度，本文档要求实现以下 10 类功能，其中前 8 类为必须完成，后 2 类可作为增强功能；如果小组希望替换某个模块，应确保替换后的功能同样适合 Java 实现并便于测试。

1. 任务待办管理。用户可以新增、查看、修改、删除待办任务。每条任务应至少包含标题、描述、优先级、截止日期和完成状态。程序应支持将任务标记为已完成或未完成，并能按状态或优先级筛选任务。该功能需要明确处理标题为空、日期格式错误、优先级非法、删除不存在任务等情况。

2. 日程提醒管理。用户可以记录课程、会议、考试、个人安排等日程事项。每条日程应包含名称、日期时间、地点和备注。程序应支持按日期查看日程，并能识别同一时间段的重复或冲突安排。基于课程实验范围，程序不要求真正调用系统通知，但应能在查询时显示即将开始或已过期的日程状态。

3. 学习计划管理。用户可以创建学习目标，例如“本周完成 Java 单元测试学习”或“复习软件测试第 3 章”，并记录计划开始日期、截止日期、预期投入时间和完成进度。程序应支持更新进度、判断是否逾期、统计已完成与未完成计划数量。该功能便于设计分支判断和边界值测试，例如进度为 0%、100%、超过 100% 或负数时的处理。

4. 收支记录管理。用户可以记录收入和支出，字段包括金额、类别、日期和备注。程序应支持查看全部记录、按类别或日期范围查询记录，并计算收入总额、支出总额和结余。程序应拒绝负金额、零金额、非法日期和未知收支类型。该功能是测试重点之一，因为金额计算、分类筛选和边界输入都适合白盒与黑盒测试。

5. 健康信息记录。用户可以记录饮水、运动、睡眠或体重等简单健康数据。程序应至少支持一种数值型健康记录和一种时长型健康记录，例如体重、睡眠时长或运动时长。程序应支持按日期查看记录并进行简单统计，如平均睡眠时长、累计运动时长。程序应对不合理数据给出提示，例如睡眠时长小于 0 或大于 24 小时。

6. 个人笔记或日记管理。用户可以新增、查看、修改、删除文本笔记。笔记应包含标题、内容、创建日期和标签。程序应支持按关键字或标签查询笔记。该功能应处理空标题、空内容、关键字无匹配、修改不存在记录等情况。

7. 联系人或常用信息管理。用户可以维护常用联系人、老师联系方式、课程群信息或常用网址等信息。每条记录应至少包含名称、类型和联系方式或链接。程序应支持查询、修改和删除。若记录电话号码或邮箱，应进行基本格式校验；如果选择常用网址，则应校验链接非空且格式合理。该功能可用于体现输入格式校验和异常处理。

8. 数据查询与汇总统计。程序应提供跨模块的查询或汇总能力，例如查看今日待办和日程、查看本周学习计划完成情况、查看本月收支统计、查看健康记录摘要。统计结果应来自已录入的数据，而不是固定文本。该功能用于体现多个业务模块之间的数据读取和汇总逻辑，也便于在实验报告中展示测试结果分析。

9. 数据持久化。作为增强功能，程序可以将用户数据保存到本地文件，并在下次启动时读取。推荐使用文本文件、CSV、JSON 或 Java 序列化中的一种简单方式。若实现持久化，应处理文件不存在、文件为空、文件内容格式错误、保存失败等情况。若小组时间有限，可以将持久化作为可选功能，但需要在需求和报告中说明数据仅在单次运行期间有效。

10. 导出实验演示数据或报告摘要。作为增强功能，程序可以导出任务列表、收支统计或测试演示数据到文本文件，便于放入实验报告或答辩视频展示。该功能不是课程实验的硬性要求，但有助于体现结果可追踪和可复现。

## 交互与数据要求

程序应提供清晰的菜单或操作入口，使用户能够选择不同功能模块。每个操作应给出明确提示，输入成功后反馈操作结果，输入失败时说明失败原因。错误提示不需要复杂，但应能让用户知道是字段为空、格式错误、范围非法，还是记录不存在。

应用数据可以存放在内存集合中，也可以持久化到本地文件。基于测试和答辩需要，建议提供一组可重复录入或初始化的示例数据，使测试用例执行前的初始状态可控。对于涉及日期、金额、时长、百分比等字段的功能，应统一输入格式和取值范围，避免同一类数据在不同模块中解释不一致。

记录类数据应具有唯一标识，便于修改和删除。唯一标识可以由程序自动生成，也可以由用户输入，但应避免因同名记录导致无法定位的情况。基于可测性考虑，推荐由程序为任务、日程、笔记等记录生成递增编号。

## 非功能与代码质量要求

程序应体现较好的 Java 编码规范。类名、方法名、变量名应含义明确，避免使用无意义缩写。代码结构应层级清晰，尽量区分数据模型、业务服务、输入输出或界面控制逻辑。业务判断应集中在可单独测试的方法中，避免把所有逻辑都写在 `main` 方法或界面事件中。

程序应遵循高内聚、低耦合原则。每个模块应负责相对独立的业务，例如任务服务负责任务增删改查，收支服务负责收支记录和统计。不同模块之间如果需要汇总，应通过明确的方法调用或统一的数据管理对象完成，而不是直接共享大量可变全局变量。

注释应合理说明关键设计意图、复杂判断和测试关注点，不应为每一行简单代码添加重复注释。异常处理应稳定，用户输入错误不应导致程序崩溃。对于课程实验而言，程序规模不宜过大，但必须能够支撑足够数量的白盒和黑盒测试用例。

## 测试相关需求

测试内容是本项目的重点。需求文档不仅要求应用具备不少于 8 个功能，还要求这些功能能够支持实验 1 的白盒测试和实验 2 的黑盒测试。测试设计应覆盖正常流程、异常输入、边界条件、状态变化、统计计算和跨功能组合场景。

### 实验 1：白盒测试要求

实验 1 应针对 Java 程序的核心业务类和方法制定测试计划，并使用 JUnit 运行白盒测试用例。推荐使用 JUnit 5；如使用 JUnit 4，应在报告中说明版本。白盒测试不应只测试菜单输入输出，而应直接测试业务逻辑方法，例如任务新增方法、日期校验方法、收支统计方法、进度更新方法、健康数据统计方法、关键字查询方法等。

白盒测试计划应说明测试目标、测试范围、测试环境、测试工具和测试策略。测试目标应包括验证核心业务逻辑正确性、验证异常输入处理、验证分支路径覆盖、发现代码缺陷或可测性问题。测试范围应覆盖至少 6 个核心模块，并优先覆盖计算和判断逻辑较多的模块。测试环境应说明 Java 版本、IDE 或构建工具、JUnit 版本和操作系统。测试工具至少应包含 JUnit，若使用 Maven 或 Gradle 管理测试，也应在报告和提交材料中说明。

白盒测试用例应体现结构性设计方法。至少应包括语句覆盖、判定覆盖、条件覆盖或基本路径测试中的若干种，不能只列出随意输入。对于收支统计，应测试收入、支出、空记录、日期范围过滤、非法金额等路径；对于任务管理，应测试新增成功、标题为空、优先级非法、标记完成、删除不存在任务等路径；对于学习计划，应测试进度边界 0%、100%、越界值和逾期判断；对于健康记录，应测试合法范围和非法范围；对于查询功能，应测试有匹配、无匹配、关键字为空等路径。

白盒测试结果应记录每个测试用例的编号、被测类或方法、输入数据、预期结果、实际结果和是否通过。若发现缺陷，应说明缺陷表现、可能原因、修改方式和复测结果。若发现某些代码难以测试，应分析可测性问题，例如业务逻辑与控制台输入耦合过强、方法返回值不明确、数据状态难以初始化等，并说明是否进行了重构。

### 实验 2：黑盒测试要求

实验 2 应针对实验 1 完成的同一应用程序制定黑盒测试计划，并使用手工测试方式运行黑盒测试用例。黑盒测试应从用户视角验证功能是否满足需求，而不是关注内部代码路径。测试计划同样应说明测试目标、测试范围、测试环境、测试工具和测试策略。

黑盒测试应覆盖所有必须功能模块，尤其是任务待办、日程、学习计划、收支、健康记录、笔记、联系人或常用信息、统计汇总这 8 个功能。测试方法应包括等价类划分、边界值分析、错误推测和场景测试。对于金额、日期、时长、进度、关键字等输入，应明确有效等价类和无效等价类；对于数值边界，应测试最小有效值、最大有效值、刚好越界值；对于流程类功能，应测试新增后查询、修改后查看、删除后再次查询、统计前后数据变化等场景。

黑盒测试用例应适合手工执行。每条用例应包含用例编号、测试目的、前置条件、操作步骤、输入数据、预期结果、实际结果和测试结论。测试执行时应记录失败用例和异常表现，不能只写“全部通过”。如果某项功能未实现或行为与需求不一致，应在结果分析中明确说明偏差及原因。

黑盒测试结果分析应说明各功能模块的通过情况、缺陷分布、用户体验问题和改进建议。分析应结合实际测试数据，例如某类非法输入是否均被拦截、统计结果是否与手工计算一致、删除或修改操作是否能正确更新后续查询结果。为了体现创新性，可以增加组合场景分析，例如“添加任务和日程后查看今日摘要”“录入多笔收支后按月份统计”“学习计划进度更新后查看完成率”等。

## 实验报告与提交物要求

最终实验报告应覆盖实验 1 和实验 2 的测试计划、测试用例、测试结果分析和实验总结。报告中应删除模板中的说明性占位文字，保留课程要求的结构和格式。实验 1 部分应重点呈现白盒测试计划、JUnit 测试用例和执行结果；实验 2 部分应重点呈现黑盒测试计划、手工测试用例和执行结果。实验总结应列出小组成员各自的心得体会。

提交材料应包括实验报告、答辩视频和其它文档。其它文档中应包含待测程序源代码、开发和运行环境说明、单元测试脚本。源代码和单元测试用例应按课程说明命名并压缩提交。答辩视频应展示应用主要功能、白盒测试运行结果、黑盒测试执行过程或结果记录，以及对缺陷和测试结果的简要分析。

## 范围边界

本项目不要求实现账号登录、云端同步、多人协作、复杂权限管理、移动端应用或真实系统通知。除非小组自行扩展，程序默认面向单个本地用户使用。数据规模也不要求达到生产系统水平，只需能支撑课程实验、测试用例设计和答辩演示。

本项目也不要求追求复杂界面效果。若界面实现会挤占测试设计和代码质量时间，应优先保证核心业务功能完整、代码结构清晰、测试用例充分、测试结果分析可信。用户原始需求强调“尤其着重测试部分”，因此功能复杂度应服务于测试覆盖，而不是为了增加界面展示效果而降低可测性。

## 验收标准

项目完成时，应至少满足以下标准：应用使用 Java 实现并能够正常运行；必须功能不少于 8 个，且每个功能可演示、可输入、可产生明确结果；核心代码命名规范、层级清晰、业务逻辑可被 JUnit 测试；实验 1 有完整测试计划、白盒测试用例、JUnit 运行结果和结果分析；实验 2 有完整测试计划、黑盒手工测试用例、执行记录和结果分析；实验报告符合模板结构，提交材料包含源代码、运行环境说明和单元测试脚本。

如果小组在实现过程中对功能范围进行调整，应保证不低于“Java 实现、个人助手、功能不少于 8 个、测试内容充分”这四个核心约束，并在实验报告中说明调整原因。
