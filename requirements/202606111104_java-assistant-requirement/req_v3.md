# Java AI 个人学习与生活助手实验 1 需求文档

本需求文档面向“软件质量保证与测试”课程实验 1 使用，目标是定义一个适合 Java 实现、功能数量不少于 8 个、结构清晰且便于开展白盒测试的 AI 个人助手程序。用户原始需求要求“适用 Java”“功能不少于 8 个”“尤其着重测试部分”；本轮迭代进一步明确实验一的助手应定位为 AI 助手，需要接入 DeepSeek Flash 大模型，同时测试部分必须区分单元测试与真实文件 I/O 验证、补充回归测试要求、强化白盒覆盖证据，并系统覆盖状态变化和跨模块交互。

本版需求将范围限定为实验 1：完成 Java 待测程序、测试计划、白盒测试用例、JUnit 单元测试执行记录、必要的组件或集成测试说明、测试结果分析、缺陷修复与回归测试记录，以及实验 1 报告内容。实验 2 的黑盒手工测试不作为本轮交付范围。

## 需求背景与目标

本项目需要开发一个简单但结构清晰的 Java AI 个人助手程序，作为“软件质量保证与测试”课程实验 1 的待测对象。根据实验指导书，实验 1 的重点是白盒测试技术应用：先完成一个个人助手类应用程序，再制定测试计划，设计白盒测试用例，使用 JUnit 等单元测试工具运行测试用例，记录测试结果，并根据测试结果分析缺陷或可测性问题。

本应用建议定位为“大学生 AI 学习与生活助手”。这一定位是基于课程实验场景、个人助手程序要求以及本轮 todo 明确提出的 AI 助手要求作出的合理整合。应用既要提供任务、日程、学习计划、收支、健康、笔记等传统个人助手能力，也要通过大模型提供自然语言问答、计划建议、摘要生成或输入解析等 AI 辅助能力。学习和生活管理场景天然包含较多判断分支、边界输入、异常路径、状态变化、统计计算和外部服务失败场景，适合作为白盒测试材料。

程序应使用 Java 开发。默认可以实现为命令行交互程序，以降低界面复杂度并突出业务逻辑和测试设计；如小组希望使用 Swing、JavaFX 或其他界面形式，也应保证核心业务逻辑与界面层分离，使 JUnit 单元测试能够直接覆盖核心类和方法。本项目的关键不是界面效果，而是提供一个可运行、可演示、可测试、便于分析测试结果的 Java 待测程序。

## 本轮范围说明

本轮只需要完成实验 1 相关工作。需求范围包括 Java AI 个人助手程序本身、实验 1 测试计划、白盒测试用例设计、JUnit 单元测试脚本、测试执行结果记录、覆盖证据、缺陷修复与回归测试记录、缺陷或可测性问题分析、实验 1 报告内容，以及提交所需的源代码和单元测试脚本。

实验 2 的黑盒测试计划、黑盒手工测试用例和黑盒测试结果分析不属于本轮必须完成内容。参考材料中关于实验 2 的说明可作为后续扩展背景理解，但本版需求不要求为实验 2 设计或执行黑盒测试。

## 目标用户与使用场景

目标用户是需要管理日常学习和生活信息的大学生。用户希望在一个轻量工具中记录待办任务、课程或日程、学习计划、收支、健康情况、个人笔记和常用信息，并能查询、修改、删除、统计这些信息。用户还希望通过 AI 助手以自然语言方式获得学习计划建议、任务拆解建议、笔记摘要、日程安排建议或对已有记录的解释性总结。

典型使用场景包括：用户添加一项课程作业并设置截止日期，随后查看未完成任务；用户询问 AI 如何把“下周完成软件测试复习”拆成可执行计划；用户记录一笔午餐支出并查看本月收支汇总；用户登记一次运动或睡眠记录并查看健康统计；用户添加学习计划并更新完成进度；用户通过关键字查询笔记并让 AI 生成摘要；用户维护老师联系方式或常用课程网址；用户在实验报告或答辩中展示核心业务方法的 JUnit 测试结果、覆盖证据、发现的问题、修复过程和回归测试记录。

程序应支持用户在本地完成基本数据管理。AI 能力需要联网调用 DeepSeek API，但不要求实现账号系统、云端同步、多人协作或复杂权限控制。若网络不可用、API Key 未配置或模型接口返回错误，程序应给出明确提示，并保证本地非 AI 功能仍可继续使用。

## AI 接入要求

实验一的助手应接入 DeepSeek Flash 大模型。模型接口按 OpenAI 兼容方式调用，`base_url` 为 `https://api.deepseek.com`，模型名称为 `deepseek-v4-flash`。API Key 不应硬编码在源码中，建议通过环境变量、配置文件或启动参数提供，并在开发和运行环境说明中写明配置方式。

AI 能力应服务于个人学习与生活助手场景，而不是做成与本地数据无关的通用聊天工具。程序至少应支持以下 AI 辅助能力中的若干项，并保证其中至少一项能够结合本地记录产生结果：自然语言问题回答、学习计划拆解、任务优先级建议、日程安排建议、笔记摘要、健康或收支记录的解释性总结、将用户自然语言输入解析为结构化待办或学习计划草稿。

AI 调用应通过独立的客户端接口或服务类封装，使业务代码不直接依赖具体 HTTP 调用细节。基于可测试性要求，单元测试中不应真实连接 DeepSeek API，而应使用 mock、stub 或 fake client 模拟正常响应、超时、鉴权失败、限流、空响应和格式异常等情况。真实 API 连通性可作为组件测试或集成测试单独验证，并且需要与 JUnit 单元测试边界区分清楚。

AI 返回内容可能不稳定，因此涉及 AI 的自动化测试不应断言完整自然语言文本完全一致。对 AI 相关单元测试，应重点断言请求参数构造是否正确、模型名称和 base_url 是否使用正确、异常是否被正确转换、超时或失败时本地功能是否保持可用、结构化解析结果是否遵循约定格式。若做真实接口验证，应将其标注为集成测试，并说明需要网络和有效 API Key。

## 功能需求

应用至少应实现 8 个可独立演示和测试的功能模块。为了保证功能数量和测试覆盖度，本文档要求实现以下 10 类功能，其中前 8 类为必须完成，后 2 类可作为增强功能；如果小组希望替换某个模块，应确保替换后的功能同样适合 Java 实现，并且能够产生足够的白盒测试场景。

1. AI 问答与建议。用户可以向 AI 助手提出与学习、任务、日程或个人记录相关的问题。程序应能构造请求、调用 DeepSeek Flash、展示回复，并在失败时返回明确错误信息。该功能应支持至少一种结合本地数据的场景，例如基于今日任务和日程生成安排建议，或基于学习计划生成拆解建议。

2. 任务待办管理。用户可以新增、查看、修改、删除待办任务。每条任务应至少包含标题、描述、优先级、截止日期和完成状态。程序应支持将任务标记为已完成或未完成，并能按状态或优先级筛选任务。该功能需要明确处理标题为空、日期格式错误、优先级非法、删除不存在任务、重复标记完成、撤销完成等情况。

3. 日程提醒管理。用户可以记录课程、会议、考试、个人安排等日程事项。每条日程应包含名称、日期时间、地点和备注。程序应支持按日期查看日程，并能识别同一时间段的重复或冲突安排。基于课程实验 1 范围，程序不要求真正调用系统通知，但应能在查询时显示即将开始、正常进行或已过期等状态。

4. 学习计划管理。用户可以创建学习目标，例如“本周完成 Java 单元测试学习”或“复习软件测试第 3 章”，并记录计划开始日期、截止日期、预期投入时间和完成进度。程序应支持更新进度、判断是否逾期、统计已完成与未完成计划数量，并可将计划内容交给 AI 生成拆解建议。该功能应明确处理进度为 0%、100%、小于 0、大于 100、截止日期早于开始日期等情况。

5. 收支记录管理。用户可以记录收入和支出，字段包括金额、类别、日期和备注。程序应支持查看全部记录、按类别或日期范围查询记录，并计算收入总额、支出总额和结余。程序应拒绝负金额、零金额、非法日期、未知收支类型和开始日期晚于结束日期的查询。该功能是测试重点之一，因为金额计算、分类筛选、日期范围判断和异常输入都适合白盒测试。

6. 健康信息记录。用户可以记录饮水、运动、睡眠或体重等简单健康数据。程序应至少支持一种数值型健康记录和一种时长型健康记录，例如体重、睡眠时长或运动时长。程序应支持按日期查看记录并进行简单统计，如平均睡眠时长、累计运动时长或平均饮水量。程序应对不合理数据给出提示，例如睡眠时长小于 0 或大于 24 小时、运动时长为负数、体重超出合理范围等。

7. 个人笔记或日记管理。用户可以新增、查看、修改、删除文本笔记。笔记应包含标题、内容、创建日期和标签。程序应支持按关键字或标签查询笔记，并可调用 AI 对指定笔记或查询结果生成摘要。该功能应处理空标题、空内容、关键字无匹配、关键字为空、修改不存在记录、删除不存在记录等情况。

8. 联系人或常用信息管理。用户可以维护常用联系人、老师联系方式、课程群信息或常用网址等信息。每条记录应至少包含名称、类型和联系方式或链接。程序应支持查询、修改和删除。若记录电话号码或邮箱，应进行基本格式校验；如果选择常用网址，则应校验链接非空且格式合理。该功能用于体现字符串格式校验、分支判断和异常处理。

9. 数据查询与汇总统计。程序应提供跨模块的查询或汇总能力，例如查看今日待办和日程、查看本周学习计划完成情况、查看本月收支统计、查看健康记录摘要、生成可供 AI 总结的本地上下文。统计结果应来自已录入的数据，而不是固定文本。该功能用于体现多个业务模块之间的数据读取和汇总逻辑，也便于在实验 1 中测试组合状态和统计路径。

10. 数据持久化与导出。作为增强功能，程序可以将用户数据保存到本地文件，并在下次启动时读取，也可以导出任务列表、收支统计、学习计划进度、AI 建议或测试演示数据到文本文件，便于放入实验报告或答辩材料。推荐使用文本文件、CSV、JSON 或 Java 序列化中的一种简单方式。若实现持久化或导出，应处理文件不存在、文件为空、文件内容格式错误、路径非法、保存失败等情况。若小组时间有限，可以将持久化和导出作为可选功能，但需要在报告中说明数据仅在单次运行期间有效。

## 交互与数据要求

程序应提供清晰的菜单或操作入口，使用户能够选择不同功能模块。每个操作应给出明确提示，输入成功后反馈操作结果，输入失败时说明失败原因。错误提示不需要复杂，但应能让用户知道是字段为空、格式错误、范围非法、记录不存在、AI 服务不可用，还是当前操作与已有状态冲突。

应用数据可以存放在内存集合中，也可以持久化到本地文件。基于测试和答辩需要，建议提供一组可重复录入或初始化的示例数据，使测试用例执行前的初始状态可控。对于涉及日期、金额、时长、百分比等字段的功能，应统一输入格式和取值范围，避免同一类数据在不同模块中解释不一致。

记录类数据应具有唯一标识，便于修改和删除。唯一标识可以由程序自动生成，也可以由用户输入，但应避免因同名记录导致无法定位的情况。基于可测性考虑，推荐由程序为任务、日程、学习计划、笔记等记录生成递增编号，并在测试中允许通过可控方式初始化编号或查询生成结果。

AI 对话或建议结果如果需要保存，应明确与普通笔记或任务数据的关系。例如，AI 生成的学习计划拆解可以先作为草稿展示，只有用户确认后才转为正式学习计划或任务记录。这样可以避免模型输出直接污染本地数据，也便于测试“生成建议”“用户确认”“用户取消”“转为正式记录”等状态变化。

## 非功能与代码质量要求

程序应体现较好的 Java 编码规范。类名、方法名、变量名应含义明确，避免使用无意义缩写。代码结构应层级清晰，尽量区分数据模型、业务服务、AI 客户端、输入输出或界面控制逻辑。业务判断应集中在可单独测试的方法中，避免把所有逻辑都写在 `main` 方法或界面事件中。

程序应遵循高内聚、低耦合原则。每个模块应负责相对独立的业务，例如任务服务负责任务增删改查，收支服务负责收支记录和统计，健康服务负责健康数据校验与汇总，AI 服务负责请求构造、响应解析和错误转换。不同模块之间如果需要汇总，应通过明确的方法调用或统一的数据管理对象完成，而不是直接共享大量可变全局变量。

注释应合理说明关键设计意图、复杂判断和测试关注点，不应为每一行简单代码添加重复注释。异常处理应稳定，用户输入错误、网络错误或模型接口错误不应导致程序崩溃。对于课程实验而言，程序规模不宜过大，但必须能够支撑足够数量、足够多样的白盒测试用例。

为了提高可测试性，核心业务方法应尽量返回明确结果或抛出明确异常，而不是只在控制台打印文本。涉及当前日期、文件路径、初始数据、网络请求、API Key、AI 客户端等外部状态的逻辑，应通过参数、接口或可替换对象传入，避免 JUnit 单元测试依赖不可控环境。

## 实验 1 测试相关需求

测试内容是本项目的重点。本轮只要求实验 1，因此测试工作应围绕白盒测试和 Java 单元测试展开，同时对真实文件 I/O 和真实 AI API 调用单独划分组件测试或集成测试边界。测试设计应覆盖正常流程、异常输入、边界条件、分支判断、状态变化、统计计算、跨功能组合场景和外部依赖失败处理。测试用例不能只列出少量“新增成功”“查询成功”的简单例子，而应体现测试方法的多样性和对代码逻辑的深入理解。

### 测试分层要求

JUnit 单元测试应保持在单元级别，主要验证业务类、工具类、状态流转类、统计类、AI 请求构造与响应处理类的逻辑。单元测试不应真实连接 DeepSeek API，不应依赖真实用户目录、真实演示数据文件或固定外部资源。对 AI 客户端、文件仓储、系统时间等外部依赖，应使用 mock、stub、fake 或测试替身隔离。

真实文件读写、文件格式兼容、导出文件生成、DeepSeek API 连通性、网络超时配置等内容可以测试，但应归入组件测试或集成测试，并与单元测试分开记录。组件或集成测试可以使用临时目录、测试专用文件和可选的真实 API Key；如果执行条件不稳定，应在报告中说明前置条件、执行方式和未纳入常规单元测试的原因。

这种分层的目的不是减少测试内容，而是避免把“实验 1 的白盒单元测试”变成依赖外部环境的脆弱测试。单元测试负责证明核心逻辑在隔离条件下正确，组件或集成测试负责证明文件系统、网络接口等真实外部资源衔接可用。

### 测试计划要求

实验 1 测试计划应说明测试目标、测试范围、测试环境、测试工具、测试分层和测试策略。

测试目标应包括：验证核心业务逻辑正确性，验证异常输入处理，验证主要判断分支和条件组合，验证状态变化和跨模块同步，验证 AI 调用封装在正常与异常情况下的行为，发现代码缺陷，发现业务逻辑与输入输出、文件系统或网络请求耦合过强等可测性问题，并通过必要修改提高程序质量。

测试范围应覆盖所有 8 个必须功能中的核心业务逻辑，并优先覆盖计算、校验、筛选、状态更新、AI 请求构造、AI 错误处理和统计汇总逻辑。若实现了数据持久化或导出功能，应在组件或集成测试中为其关键成功路径和失败路径设计测试；若将文件仓储抽象为接口，则单元测试应通过 fake 仓储验证业务层对成功和失败结果的处理。

测试环境应说明 Java 版本、IDE 或构建工具、JUnit 版本和操作系统。测试工具应至少包含 JUnit，推荐使用 JUnit 5；如使用 JUnit 4，应在报告中说明原因和版本。若使用 Maven 或 Gradle 管理项目和测试脚本，也应在报告和提交材料中说明运行命令。若使用 Mockito 或其他 mock 工具，应说明其用途。

测试策略应说明采用哪些白盒测试方法、各方法适用在哪些功能或代码片段，以及为什么这样选择。基于用户对测试方法丰富性的要求，测试策略不应只写一种方法，应至少覆盖语句覆盖、判定覆盖、条件覆盖、基本路径测试中的多种方法，并可结合边界值分析、等价类划分、错误推测、状态迁移测试和场景测试来设计单元测试输入数据。这里的边界值、等价类、状态迁移和场景链路是为白盒单元测试补充输入与路径设计依据，不改变本轮以实验 1 白盒测试为主的范围。

### 白盒测试覆盖证据要求

白盒测试不能只在报告中列出测试方法名称。报告应提供可证明的覆盖证据，使读者能够看出测试确实覆盖了关键代码路径。

至少应选择 2 到 3 个复杂核心方法进行重点说明，例如日期范围筛选收支记录、更新任务状态并刷新统计、生成今日摘要、解析 AI 结构化建议、计算学习计划完成状态或处理 AI 调用失败降级。对这些方法，应给出控制流图或文字化控制流说明，计算圈复杂度，列出独立路径，并说明每条独立路径对应的测试用例。

对于包含复合条件的方法，应说明判定覆盖、条件覆盖或条件组合覆盖如何达成。例如，可以展示“标题非空、日期合法、优先级合法”的条件组合测试，也可以展示“金额大于 0、类型合法、日期范围合法”的条件覆盖设计。

报告中应附上覆盖结果或映射证据。可选形式包括 JaCoCo 等覆盖工具生成的 branch/condition coverage 结果、方法-用例映射表、独立路径-用例映射表、关键分支覆盖表。若没有使用覆盖工具，也必须通过表格说明每个核心方法的主要分支、对应测试用例和覆盖结论，避免只用“已覆盖”这类口头声明。

### 白盒测试方法要求

白盒测试应直接面向业务类和业务方法，而不是只测试控制台菜单输入输出。推荐测试对象包括 AI 服务、任务服务、日程服务、学习计划服务、收支服务、健康记录服务、笔记服务、联系人或常用信息服务、统计汇总服务，以及日期校验、金额校验、进度校验、关键字查询、请求参数构造、响应解析等工具方法。

测试方法应尽量多样。语句覆盖可用于保证核心新增、修改、删除、查询、AI 调用包装和统计语句被执行。判定覆盖可用于测试 `if/else`、`switch`、异常分支和返回状态分支。条件覆盖可用于测试多个条件组合，例如“标题非空且日期合法且优先级合法”或“AI 返回非空且格式合法且用户确认导入”。基本路径测试可用于覆盖包含多分支、多返回值或循环的业务方法，例如按日期范围筛选收支记录、计算学习计划完成率、生成今日摘要、解析 AI 计划建议等。

对于每个必须功能，测试用例至少应覆盖成功路径、典型失败路径、边界输入和状态变化。为了体现用例设计的详尽性，建议每个必须功能至少设计 4 类以上单元测试场景，整体 JUnit 单元测试用例数量不应只停留在十几条；如果功能实现较完整，建议达到 30 条以上有代表性的单元测试用例，并在实验报告中选择关键用例进行说明。

### 状态变化与跨模块交互测试要求

本项目不能只测试单个 CRUD 操作，还应系统测试状态变化和跨模块交互。测试计划中应明确列出主要状态、状态迁移、基本流、备选流和异常流。

任务模块至少应测试“未完成 -> 已完成 -> 重复完成 -> 撤销完成 -> 再次完成”等状态链路，并验证每一步对待办筛选和统计汇总的影响。日程模块至少应测试“即将开始 -> 进行中 -> 已过期”的状态判断，并通过可控当前时间避免测试结果随真实日期变化。学习计划模块至少应测试“未开始 -> 进行中 -> 已完成”以及“未完成但已逾期”的路径。

跨模块交互测试应覆盖数据变化后的统计同步。例如，新增任务后今日摘要应增加对应条目，删除任务后摘要应回退；新增收支记录后本月结余应更新，删除记录后统计应恢复；新增学习计划并更新进度后，本周计划完成率应同步变化；新增健康记录后健康摘要应反映累计或平均结果。若 AI 功能会读取本地摘要生成建议，应测试本地上下文为空、单模块有数据、多模块组合数据、AI 客户端失败时的降级提示。

场景链路测试应至少包含一个基本流和若干备选流。例如，基本流可以是“创建学习计划 -> AI 生成拆解建议 -> 用户确认导入任务 -> 查看今日任务 -> 完成任务 -> 统计更新”；备选流可以是“AI 返回失败 -> 用户手动创建任务”“用户取消导入 -> 本地数据不变化”“任务重复完成 -> 状态和统计不重复增加”。这些链路既可以用 JUnit 在服务层完成，也可以在报告中作为组件级场景测试记录。

### 各功能测试关注点

AI 问答与建议应测试请求构造成功、base_url 和模型名称正确、提示词包含必要本地上下文、mock 正常响应、mock 空响应、mock 超时、mock 鉴权失败、mock 限流、响应格式异常、AI 失败后本地功能仍可用、用户取消导入 AI 建议时本地数据不变化等路径。真实 DeepSeek API 连通性如需验证，应作为集成测试单独记录。

任务待办管理应测试新增成功、标题为空、优先级非法、截止日期格式错误、按状态筛选、按优先级筛选、标记完成、重复标记完成、撤销完成、修改任务、删除存在任务、删除不存在任务，以及状态变化后统计同步等路径。

日程提醒管理应测试新增日程成功、名称为空、日期时间非法、按日期查询、时间冲突识别、查询无结果、即将开始状态、进行中状态、已过期状态，以及当前时间可控时状态判断是否稳定等路径。

学习计划管理应测试创建计划成功、开始日期晚于截止日期、更新进度为 0%、更新进度为 100%、进度小于 0、进度大于 100、逾期判断、完成数量统计、AI 拆解建议生成、用户确认或取消导入拆解任务等路径。

收支记录管理应测试记录收入、记录支出、金额为 0、金额为负数、类型非法、类别筛选、日期范围筛选、空记录统计、多笔记录统计、开始日期晚于结束日期、结余计算精度、新增和删除后统计同步等路径。

健康信息记录应测试合法睡眠时长、睡眠时长为 0、睡眠时长大于 24、运动时长为负、按日期查询、平均值计算、累计值计算、无记录统计、新增和删除后健康摘要同步等路径。

个人笔记或日记管理应测试新增成功、标题为空、内容为空、按关键字查询有结果、按关键字查询无结果、关键字为空、按标签查询、修改不存在笔记、删除不存在笔记、mock AI 摘要成功、mock AI 摘要失败等路径。

联系人或常用信息管理应测试新增合法邮箱、邮箱格式非法、电话号码格式非法、网址格式非法、按名称查询、按类型查询、修改记录、删除记录、查询不存在记录等路径。

数据查询与汇总统计应测试无数据摘要、单模块有数据摘要、多模块组合摘要、今日待办和日程统计、本周学习计划统计、本月收支统计、健康记录摘要，以及新增、修改、删除、状态变化、AI 建议导入或取消后统计结果是否同步变化。

若实现数据持久化，应在组件或集成测试中测试文件不存在时初始化、保存成功、读取成功、空文件、格式错误文件和保存失败提示；单元测试中则通过 mock 或 fake 仓储验证业务层面对持久化成功和失败的处理。若实现导出功能，应测试导出成功、无数据导出、路径非法或写入失败等路径，并同样区分单元级逻辑测试与真实文件 I/O 验证。

### 测试用例记录要求

实验报告中的测试用例应清楚列出采用的测试方法及其对应测试用例。每条代表性用例应至少包含用例编号、测试层级、测试方法、被测类或方法、测试目的、前置条件、输入数据、预期结果、实际结果和是否通过。对于 JUnit 中实际执行的测试，应保证测试脚本中的方法名含义清楚，能够从名称看出被测场景。

测试数据应具体，不应只写“输入合法数据”“输入非法数据”。例如，金额测试应写出具体金额、类别和日期；进度测试应写出 `0`、`100`、`-1`、`101` 等值；日期测试应写出合法日期、非法格式、开始日期晚于结束日期等具体输入；AI 测试应写出 mock 响应、错误类型、请求模型名、是否包含本地上下文等具体断言。预期结果也应具体，例如“抛出 IllegalArgumentException”“返回 false”“统计支出总额为 58.50”“查询结果数量为 0”“AI 服务失败时返回降级提示且不新增任务”，而不是笼统写“系统提示错误”。

JUnit 单元测试脚本应能够重复运行。每个测试之间应隔离数据状态，避免前一个测试的新增或删除影响后一个测试。可以通过 `@BeforeEach` 初始化服务对象、fake 仓储、mock AI 客户端和测试数据，也可以为每个测试单独构造输入对象。单元测试不应依赖真实文件路径、真实 API Key、真实网络状态或真实当前日期；若需要这些内容，应放入组件或集成测试并单独说明。

### 缺陷修复与回归测试要求

测试结果分析应根据真实测试执行结果展开，不能只写“全部通过”。分析应说明测试总数、通过数量、失败数量、失败原因、修改方式、复测结果和回归测试结果。若所有测试最终通过，也应说明测试过程中是否发现过缺陷、是否因为测试暴露了可测性问题而调整代码结构。

每次缺陷修复都必须新增或保留能够复现该缺陷的测试用例。修复后不仅要重跑该复现用例，还应重跑受影响模块的相关测试，以及一组核心回归测试集。核心回归测试集至少应覆盖任务状态变化、日程状态判断、学习计划进度、收支统计、数据汇总、AI 调用失败降级等关键路径。若接口、数据结构或跨模块汇总逻辑发生变化，应对所有依赖该接口或数据的模块进行回归测试。

缺陷记录应包含缺陷表现、触发输入、预期结果、实际结果、可能原因、修复方式、新增复现用例编号、重跑范围和回归结论。典型缺陷可以包括金额统计遗漏支出、日期边界判断错误、进度 100% 时未自动视为完成、重复完成任务导致统计重复增加、删除记录后统计未更新、AI 失败导致主流程崩溃、空关键字查询返回异常等。

如果发现某些代码难以测试，应分析可测性问题，例如业务逻辑与控制台输入耦合过强、方法只打印结果不返回值、使用静态全局集合导致测试互相影响、当前日期不可控导致测试结果不稳定、文件路径写死、AI 客户端无法替换、异常类型不明确导致断言困难等。需求允许并鼓励根据测试结果对代码进行小幅重构，使核心逻辑更容易被 JUnit 覆盖。

结果分析应体现测试方法的价值。例如，可以说明哪类测试发现了边界缺陷，哪类测试覆盖了复杂分支，哪类测试验证了统计结果与手工计算一致，哪类测试暴露了模块耦合问题，哪类回归测试证明修复没有破坏既有功能。这样能更好地回应课程评分中“测试结果分析充分、合理，能体现创新性”的要求。

## 范围边界

本项目不要求实现账号登录、云端同步、多人协作、复杂权限管理、移动端应用或真实系统通知。除非小组自行扩展，程序默认面向单个本地用户使用。数据规模也不要求达到生产系统水平，只需能支撑课程实验 1、白盒测试用例设计和答辩演示。

本项目要求接入 DeepSeek Flash，但不要求训练模型、微调模型、搭建模型服务或实现复杂智能体框架。AI 能力应保持轻量，重点用于学习与生活助手场景，并通过良好封装保证可测试性。若真实网络条件受限，可以在演示中说明真实 API 配置方式，并通过 mock 或 stub 展示单元测试和降级逻辑，但程序设计上仍应保留按要求调用 `https://api.deepseek.com` 和 `deepseek-v4-flash` 的能力。

本项目也不要求追求复杂界面效果。若界面实现会挤占测试设计和代码质量时间，应优先保证核心业务功能完整、代码结构清晰、AI 调用封装合理、测试用例充分、JUnit 脚本可运行、覆盖证据可信、回归测试记录明确。用户原始需求强调“尤其着重测试部分”，本轮 todo 又强调测试分层、覆盖证据、回归测试和状态链路，因此功能复杂度应服务于测试覆盖，而不是为了增加界面展示效果而降低可测性。
