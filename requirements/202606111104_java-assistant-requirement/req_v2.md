# Java 个人学习与生活助手实验 1 需求文档

本需求文档面向“软件质量保证与测试”课程实验 1 使用，目标是定义一个适合 Java 实现、功能数量不少于 8 个、结构清晰且便于开展白盒测试的个人助手程序。用户原始需求要求“适用 Java”“功能不少于 8 个”“尤其着重测试部分”；本轮迭代进一步明确“本项目目前只需要做实验 1”，并强调测试方法要多样、丰富，测试用例要详尽、用心设计。因此，本版需求将范围收敛到实验 1：完成 Java 待测程序、测试计划、白盒测试用例、JUnit 单元测试执行记录、结果分析和实验 1 报告内容；实验 2 的黑盒手工测试不作为本轮交付范围。

## 需求背景与目标

本项目需要开发一个简单但结构清晰的个人助手程序，作为“软件质量保证与测试”课程实验 1 的待测对象。根据实验指导书，实验 1 的重点是白盒测试技术应用：先完成一个个人助手类应用程序，再制定测试计划，设计白盒测试用例，使用 JUnit 等单元测试工具运行测试用例，记录测试结果，并根据测试结果分析缺陷或可测性问题。

本应用建议定位为“大学生个人学习与生活助手”。这一定位是基于课程实验场景、个人助手程序要求以及开发者通常为学生的背景作出的合理推断。学习、任务、日程、收支、健康、笔记等功能既贴近目标用户，也能自然形成较多判断分支、边界输入、异常路径、状态变化和统计计算，适合作为白盒测试材料。

程序应使用 Java 开发。默认可以实现为命令行交互程序，以降低界面复杂度并突出业务逻辑和测试设计；如小组希望使用 Swing、JavaFX 或其他界面形式，也应保证核心业务逻辑与界面层分离，使 JUnit 单元测试能够直接覆盖核心类和方法。本项目的关键不是界面效果，而是提供一个可运行、可演示、可测试、便于分析测试结果的 Java 待测程序。

## 本轮范围说明

本轮只需要完成实验 1 相关工作。也就是说，需求范围包括 Java 个人助手程序本身、实验 1 测试计划、白盒测试用例设计、JUnit 测试脚本、测试执行结果记录、缺陷或可测性问题分析、实验 1 报告内容，以及提交所需的源代码和单元测试脚本。

实验 2 的黑盒测试计划、黑盒手工测试用例和黑盒测试结果分析不属于本轮必须完成内容。参考材料中关于实验 2 的说明可作为后续扩展背景理解，但本版需求不要求为实验 2 设计或执行黑盒测试。

## 目标用户与使用场景

目标用户是需要管理日常学习和生活信息的大学生。用户希望在一个轻量工具中记录待办任务、课程或日程、学习计划、收支、健康情况、个人笔记和常用信息，并能查询、修改、删除、统计这些信息。程序应支持用户在本地完成基本数据管理，不要求联网、多人协作或复杂权限控制。

典型使用场景包括：用户添加一项课程作业并设置截止日期，随后查看未完成任务；用户记录一笔午餐支出并查看本月收支汇总；用户登记一次运动或睡眠记录并查看健康统计；用户添加学习计划并更新完成进度；用户通过关键字查询笔记；用户维护老师联系方式或常用课程网址；用户在实验报告或答辩中展示核心业务方法的 JUnit 测试结果、覆盖的代码路径、发现的问题和改进过程。

## 功能需求

应用至少应实现 8 个可独立演示和测试的功能模块。为了保证功能数量和测试覆盖度，本文档要求实现以下 10 类功能，其中前 8 类为必须完成，后 2 类可作为增强功能；如果小组希望替换某个模块，应确保替换后的功能同样适合 Java 实现，并且能够产生足够的白盒测试场景。

1. 任务待办管理。用户可以新增、查看、修改、删除待办任务。每条任务应至少包含标题、描述、优先级、截止日期和完成状态。程序应支持将任务标记为已完成或未完成，并能按状态或优先级筛选任务。该功能需要明确处理标题为空、日期格式错误、优先级非法、删除不存在任务、重复标记完成等情况。

2. 日程提醒管理。用户可以记录课程、会议、考试、个人安排等日程事项。每条日程应包含名称、日期时间、地点和备注。程序应支持按日期查看日程，并能识别同一时间段的重复或冲突安排。基于课程实验 1 范围，程序不要求真正调用系统通知，但应能在查询时显示即将开始、正常进行或已过期等状态。

3. 学习计划管理。用户可以创建学习目标，例如“本周完成 Java 单元测试学习”或“复习软件测试第 3 章”，并记录计划开始日期、截止日期、预期投入时间和完成进度。程序应支持更新进度、判断是否逾期、统计已完成与未完成计划数量。该功能应明确处理进度为 0%、100%、小于 0、大于 100、截止日期早于开始日期等情况。

4. 收支记录管理。用户可以记录收入和支出，字段包括金额、类别、日期和备注。程序应支持查看全部记录、按类别或日期范围查询记录，并计算收入总额、支出总额和结余。程序应拒绝负金额、零金额、非法日期、未知收支类型和开始日期晚于结束日期的查询。该功能是测试重点之一，因为金额计算、分类筛选、日期范围判断和异常输入都适合白盒测试。

5. 健康信息记录。用户可以记录饮水、运动、睡眠或体重等简单健康数据。程序应至少支持一种数值型健康记录和一种时长型健康记录，例如体重、睡眠时长或运动时长。程序应支持按日期查看记录并进行简单统计，如平均睡眠时长、累计运动时长或平均饮水量。程序应对不合理数据给出提示，例如睡眠时长小于 0 或大于 24 小时、运动时长为负数、体重超出合理范围等。

6. 个人笔记或日记管理。用户可以新增、查看、修改、删除文本笔记。笔记应包含标题、内容、创建日期和标签。程序应支持按关键字或标签查询笔记。该功能应处理空标题、空内容、关键字无匹配、关键字为空、修改不存在记录、删除不存在记录等情况。

7. 联系人或常用信息管理。用户可以维护常用联系人、老师联系方式、课程群信息或常用网址等信息。每条记录应至少包含名称、类型和联系方式或链接。程序应支持查询、修改和删除。若记录电话号码或邮箱，应进行基本格式校验；如果选择常用网址，则应校验链接非空且格式合理。该功能用于体现字符串格式校验、分支判断和异常处理。

8. 数据查询与汇总统计。程序应提供跨模块的查询或汇总能力，例如查看今日待办和日程、查看本周学习计划完成情况、查看本月收支统计、查看健康记录摘要。统计结果应来自已录入的数据，而不是固定文本。该功能用于体现多个业务模块之间的数据读取和汇总逻辑，也便于在实验 1 中测试组合状态和统计路径。

9. 数据持久化。作为增强功能，程序可以将用户数据保存到本地文件，并在下次启动时读取。推荐使用文本文件、CSV、JSON 或 Java 序列化中的一种简单方式。若实现持久化，应处理文件不存在、文件为空、文件内容格式错误、保存失败等情况。若小组时间有限，可以将持久化作为可选功能，但需要在报告中说明数据仅在单次运行期间有效。

10. 导出实验演示数据或测试摘要。作为增强功能，程序可以导出任务列表、收支统计、学习计划进度或测试演示数据到文本文件，便于放入实验报告或答辩材料。该功能不是课程实验的硬性要求，但有助于体现测试结果可追踪和可复现。

## 交互与数据要求

程序应提供清晰的菜单或操作入口，使用户能够选择不同功能模块。每个操作应给出明确提示，输入成功后反馈操作结果，输入失败时说明失败原因。错误提示不需要复杂，但应能让用户知道是字段为空、格式错误、范围非法、记录不存在，还是当前操作与已有状态冲突。

应用数据可以存放在内存集合中，也可以持久化到本地文件。基于测试和答辩需要，建议提供一组可重复录入或初始化的示例数据，使测试用例执行前的初始状态可控。对于涉及日期、金额、时长、百分比等字段的功能，应统一输入格式和取值范围，避免同一类数据在不同模块中解释不一致。

记录类数据应具有唯一标识，便于修改和删除。唯一标识可以由程序自动生成，也可以由用户输入，但应避免因同名记录导致无法定位的情况。基于可测性考虑，推荐由程序为任务、日程、学习计划、笔记等记录生成递增编号，并在测试中允许通过可控方式初始化编号或查询生成结果。

## 非功能与代码质量要求

程序应体现较好的 Java 编码规范。类名、方法名、变量名应含义明确，避免使用无意义缩写。代码结构应层级清晰，尽量区分数据模型、业务服务、输入输出或界面控制逻辑。业务判断应集中在可单独测试的方法中，避免把所有逻辑都写在 `main` 方法或界面事件中。

程序应遵循高内聚、低耦合原则。每个模块应负责相对独立的业务，例如任务服务负责任务增删改查，收支服务负责收支记录和统计，健康服务负责健康数据校验与汇总。不同模块之间如果需要汇总，应通过明确的方法调用或统一的数据管理对象完成，而不是直接共享大量可变全局变量。

注释应合理说明关键设计意图、复杂判断和测试关注点，不应为每一行简单代码添加重复注释。异常处理应稳定，用户输入错误不应导致程序崩溃。对于课程实验而言，程序规模不宜过大，但必须能够支撑足够数量、足够多样的白盒测试用例。

为了提高可测试性，核心业务方法应尽量返回明确结果或抛出明确异常，而不是只在控制台打印文本。涉及当前日期、文件路径、初始数据等外部状态的逻辑，应尽量通过参数或可替换对象传入，避免 JUnit 测试依赖不可控环境。

## 实验 1 测试相关需求

测试内容是本项目的重点。本轮只要求实验 1，因此测试工作应围绕白盒测试和 Java 单元测试展开。测试设计应覆盖正常流程、异常输入、边界条件、分支判断、状态变化、统计计算和跨功能组合场景。测试用例不能只列出少量“新增成功”“查询成功”的简单例子，而应体现测试方法的多样性和对代码逻辑的深入理解。

### 测试计划要求

实验 1 测试计划应说明测试目标、测试范围、测试环境、测试工具和测试策略。

测试目标应包括：验证核心业务逻辑正确性，验证异常输入处理，验证主要判断分支和条件组合，发现代码缺陷，发现业务逻辑与输入输出耦合过强等可测性问题，并通过必要修改提高程序质量。

测试范围应覆盖所有 8 个必须功能中的核心业务逻辑，并优先覆盖计算、校验、筛选、状态更新和统计汇总逻辑。若实现了数据持久化或导出功能，也应至少为其关键成功路径和失败路径设计测试。

测试环境应说明 Java 版本、IDE 或构建工具、JUnit 版本和操作系统。测试工具应至少包含 JUnit，推荐使用 JUnit 5；如使用 JUnit 4，应在报告中说明原因和版本。若使用 Maven 或 Gradle 管理项目和测试脚本，也应在报告和提交材料中说明运行命令。

测试策略应说明采用哪些白盒测试方法、各方法适用在哪些功能或代码片段，以及为什么这样选择。基于用户本轮对测试方法丰富性的要求，测试策略不应只写一种方法，应至少覆盖语句覆盖、判定覆盖、条件覆盖、基本路径测试中的多种方法，并可结合边界值分析、等价类划分和错误推测来设计单元测试输入数据。这里的边界值和等价类是为单元测试准备输入数据的辅助方法，不改变本轮以实验 1 白盒测试为主的范围。

### 白盒测试方法要求

白盒测试应直接面向业务类和业务方法，而不是只测试控制台菜单输入输出。推荐测试对象包括任务服务、日程服务、学习计划服务、收支服务、健康记录服务、笔记服务、联系人或常用信息服务、统计汇总服务，以及日期校验、金额校验、进度校验、关键字查询等工具方法。

测试方法应尽量多样。语句覆盖可用于保证核心新增、修改、删除、查询和统计语句被执行。判定覆盖可用于测试 `if/else`、`switch`、异常分支和返回状态分支。条件覆盖可用于测试多个条件组合，例如“标题非空且日期合法且优先级合法”或“金额大于 0 且类型合法且日期范围合法”。基本路径测试可用于覆盖包含多分支、多返回值或循环的业务方法，例如按日期范围筛选收支记录、计算学习计划完成率、生成今日摘要等。

对于每个必须功能，测试用例至少应覆盖成功路径、典型失败路径、边界输入和状态变化。为了体现用例设计的详尽性，建议每个必须功能至少设计 4 类以上单元测试场景，整体 JUnit 测试用例数量不应只停留在十几条；如果功能实现较完整，建议达到 30 条以上有代表性的测试用例，并在实验报告中选择关键用例进行说明。

### 各功能测试关注点

任务待办管理应测试新增成功、标题为空、优先级非法、截止日期格式错误、按状态筛选、按优先级筛选、标记完成、重复标记、修改任务、删除存在任务、删除不存在任务等路径。

日程提醒管理应测试新增日程成功、名称为空、日期时间非法、按日期查询、时间冲突识别、查询无结果、已过期状态、即将开始状态等路径。

学习计划管理应测试创建计划成功、开始日期晚于截止日期、更新进度为 0%、更新进度为 100%、进度小于 0、进度大于 100、逾期判断、完成数量统计等路径。

收支记录管理应测试记录收入、记录支出、金额为 0、金额为负数、类型非法、类别筛选、日期范围筛选、空记录统计、多笔记录统计、开始日期晚于结束日期、结余计算精度等路径。

健康信息记录应测试合法睡眠时长、睡眠时长为 0、睡眠时长大于 24、运动时长为负、按日期查询、平均值计算、累计值计算、无记录统计等路径。

个人笔记或日记管理应测试新增成功、标题为空、内容为空、按关键字查询有结果、按关键字查询无结果、关键字为空、按标签查询、修改不存在笔记、删除不存在笔记等路径。

联系人或常用信息管理应测试新增合法邮箱、邮箱格式非法、电话号码格式非法、网址格式非法、按名称查询、按类型查询、修改记录、删除记录、查询不存在记录等路径。

数据查询与汇总统计应测试无数据摘要、单模块有数据摘要、多模块组合摘要、今日待办和日程统计、本周学习计划统计、本月收支统计、健康记录摘要，以及新增、修改、删除后统计结果是否同步变化。

若实现数据持久化，应测试文件不存在时初始化、保存成功、读取成功、空文件、格式错误文件和保存失败提示。若实现导出功能，应测试导出成功、无数据导出、路径非法或写入失败等路径。

### 测试用例记录要求

实验报告中的测试用例应清楚列出采用的测试方法及其对应测试用例。每条代表性用例应至少包含用例编号、测试方法、被测类或方法、测试目的、前置条件、输入数据、预期结果、实际结果和是否通过。对于 JUnit 中实际执行的测试，应保证测试脚本中的方法名含义清楚，能够从名称看出被测场景。

测试数据应具体，不应只写“输入合法数据”“输入非法数据”。例如，金额测试应写出具体金额、类别和日期；进度测试应写出 `0`、`100`、`-1`、`101` 等值；日期测试应写出合法日期、非法格式、开始日期晚于结束日期等具体输入。预期结果也应具体，例如“抛出 IllegalArgumentException”“返回 false”“统计支出总额为 58.50”“查询结果数量为 0”，而不是笼统写“系统提示错误”。

JUnit 测试脚本应能够重复运行。每个测试之间应尽量隔离数据状态，避免前一个测试的新增或删除影响后一个测试。可以通过 `@BeforeEach` 初始化服务对象和测试数据，也可以为每个测试单独构造输入对象。若测试文件读写，应使用临时文件或测试专用路径，避免覆盖真实演示数据。

### 测试结果分析要求

测试结果分析应根据真实测试执行结果展开，不能只写“全部通过”。分析应说明测试总数、通过数量、失败数量、失败原因、修改方式和复测结果。若所有测试最终通过，也应说明测试过程中是否发现过缺陷、是否因为测试暴露了可测性问题而调整代码结构。

如果发现缺陷，应记录缺陷表现、触发输入、预期结果、实际结果、可能原因、修复方式和复测结论。典型缺陷可以包括金额统计遗漏支出、日期边界判断错误、进度 100% 时未自动视为完成、删除记录后统计未更新、空关键字查询返回异常等。

如果发现某些代码难以测试，应分析可测性问题，例如业务逻辑与控制台输入耦合过强、方法只打印结果不返回值、使用静态全局集合导致测试互相影响、当前日期不可控导致测试结果不稳定、异常类型不明确导致断言困难等。需求允许并鼓励根据测试结果对代码进行小幅重构，使核心逻辑更容易被 JUnit 覆盖。

结果分析应体现测试方法的价值。例如，可以说明哪类测试发现了边界缺陷，哪类测试覆盖了复杂分支，哪类测试验证了统计结果与手工计算一致，哪类测试暴露了模块耦合问题。这样能更好地回应课程评分中“测试结果分析充分、合理，能体现创新性”的要求。
